## Proposed one-topic replacement pilot

**Title/experimental question:** “Can a browser automation recover when the UI changes?” (working title, not publication copy).

**Honest technical scope:** A *deterministic* automation test run in a visible real browser against a **locally controlled fixture/demo UI**. The fixture intentionally changes a button label/selectable locator so a brittle interaction fails and a preprogrammed semantic locator/retry strategy succeeds. A simulated DOM change is clearly disclosed as a controlled test. It does **not** independently prove general browser resilience, production behavior, adaptive AI reasoning or agent autonomy. Do **not** market a Playwright script as an AI agent.

**Why test this instead of SQLite for the creative experiment:** a browser session offers visible input, navigation, feedback, actual failure/recovery and a result; the previous SQLite terminal clip had 4 nearly static text outcomes. This is a *hypothesis* about shot diversity, not an assertion that the result will look professional.

## Actual visual shot inventory — minimum before editing

1. A **continuous source capture** of Chrome/Chromium *headed* mode with native readable 1080p-class screen state (OBS window capture or Playwright built-in video) demonstrating real pointer/interaction/UI response. Use local/no customer data.
2. **Actual error state** from the run, visible in the browser and/or separately captured test trace/log with identifiable attempt and reason. Error must be real within the controlled fixture, not generated afterward as fictional overlay.
3. **Actual scripted recovery** (semantic locator retry or reset) and success state in the browser, with a fresh source receipt linking the run to the displayed outcome.
4. **One independent evidence insert**: real Playwright trace/test outcome or a verified summary from the actual run. If unavailable, keep the story as experimental and do not invent a receipt.

**Minimum visually distinct action:** at least 3 meaningful screen states (interaction, failure, recovery/success) and 2 framing scales (overview and readable native capture). Do **not** fill missing footage with static slide/title templates, generic SQL terminal composites, UI mockups presented as live captures or gratuitous camera shakes.
